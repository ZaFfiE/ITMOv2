# Модель угроз: Mini Shop (Практика 6)

## Контекст и границы доверия

- Клиентские приложения/скрипты обращаются по HTTP к локальному серверу (`127.0.0.1`).
- Сервер (`service.py`) ведёт сессии в памяти, хранит данные в SQLite (in-memory), работает с одноразовой файловой песочницей (`sandbox.py`).
- AI-потоки:
  - `GET /assistant/context` — формирует текстовый контекст для внешнего планировщика LLM (отдельный процесс, запускаемый агентом).
  - `POST /assistant/execute` — выполняет заявленное действие в процессе сервера с доступом к инструментам: `read_file`, `export_profiles`, `delete_tree`.
- Песочница ограничивает доступ только пределами временного каталога, но не разграничивает «публичное» и «приватное» внутри него (это обязанность сервиса).

```mermaid
flowchart LR
    C[Клиент] -- HTTP (127.0.0.1) --> S[HTTP-сервер (service.py)]

    subgraph PROC[Процесс сервера]
      S --> DB[(SQLite in-memory)]
      S --> FS[(Файловая песочница\n(sandbox.py))]
      S --> LOG[(Логи запросов\nв памяти)]
      S <-->|/assistant/context| LLM[(Внешний планировщик\nLLM-агент)]
      S --> TOOLS{Инструменты}
      TOOLS -->|read_file| FS
      TOOLS -->|export_profiles| DB
      TOOLS -->|delete_tree| FS
    end
```

## Активы

- Персональные данные (учебные): профили (имя, email, адрес) в SQLite.
- Содержимое чеков пользователей в файловой песочнице.
- Закрытая служебная заметка `private/operator-note.txt` в песочнице.
- Сессии и токены (`X-Token`).
- Журнал запросов с телами и заголовками.
- Заказы и цены каталога.

## Акторы и доверие

- Клиент (аутентифицированный/неаутентифицированный).
- Сотрудник (роль staff).
- Внешний LLM-планировщик (возвращает JSON-решение, не исполняет код).
- Сервер — доверенная зона исполнения инструментов, обязан проверять права вне зависимости от поведения LLM.

## Основные угрозы и поверхности атаки

1) SQL Injection (SQLi)
   - Поверхность: `GET /profile?id=...`, `GET /search?q=...` (форматирование SQL через f-строки).
   - Эффект: чтение чужих профилей, возможные манипуляции данными.

2) IDOR (несанкционированный доступ по идентификатору)
   - Поверхность: `GET /profile?id=...` игнорирует владельца сессии; `GET /orders` возвращает все заказы.
   - Эффект: раскрытие данных других пользователей.

3) Path Traversal внутри песочницы
   - Поверхность: `GET /files?user=...&path=...` (сборка пути `files/{user}/{path}` без нормализации).
   - Эффект: доступ к `private/operator-note.txt` через `..`-секвенции; чтение чужих чеков.

4) Stored XSS
   - Поверхность: `POST /reviews` + `GET /reviews/view` (сырой HTML из пользовательского ввода).
   - Эффект: выполнение JS при открытии страницы в браузере (например, кража токена при отображении UI).

5) Утечки через `/debug/logs`
   - Поверхность: `GET /debug/logs` открыто возвращает полный журнал (тела, заголовки, токены).
   - Эффект: раскрытие чувствительной информации и последующая эскалация.

6) Эскалация ролей через заголовок
   - Поверхность: `GET /admin/export` полагается на `X-Role: staff`.
   - Эффект: неаутентифицированный клиент может выдавать себя за staff и экспортировать профили.

7) Небезопасный `/assistant/execute`
   - Поверхность: нет обязательной сессии/ролей, инструменты доступны напрямую.
   - Эффект: чтение всех профилей (`export_profiles`), удаление данных (`delete_tree`), чтение любых файлов в песочнице.

8) Подмена цены в заказе
   - Поверхность: `POST /orders` принимает произвольный `price` от клиента.
   - Эффект: покупка товара по заниженной цене, нарушение целостности бизнес-правил.

9) Prompt Injection (LLM как планировщик)
   - Поверхность: вредоносный текст в отзывах попадает в контекст `GET /assistant/context`, побуждая LLM вернуть опасное решение.
   - Эффект: при отсутствии серверных проверок приводит к выполнению опасных инструментов.

## Приоритизация (Impact × Likelihood)

- Высокий
  - Небезопасный `/assistant/execute`: удаление файлов и массовое раскрытие данных.
  - Эскалация ролей заголовком на `/admin/export`.
  - Path Traversal в `/files` с доступом к `private/operator-note.txt`.
  - SQLi в `/profile` и `/search`.

- Средний
  - IDOR: чтение чужих профилей/заказов без SQLi.
  - Утечки через `/debug/logs` (с токенами/телами запросов).
  - Подмена цены в `/orders`.

- Низкий–Средний
  - Stored XSS в `reviews/view` (требует пользовательского просмотра в браузере).

## Направления mitigations (высокоуровнево)

- Аутентификация и авторизация
  - Требовать валидную сессию для всех чувствительных эндпоинтов; роль — только из сессии, игнорировать заголовки.
- Контроль доступа к данным
  - `/profile` и `/orders` — возвращать данные текущего пользователя; админские действия вынести в отдельные маршруты с ролью staff.
- Безопасность SQL
  - Параметризованные запросы (`?`/placeholders), запрет конкатенации строк.
- Файловый доступ
  - Жёсткое сопоставление только собственного чека текущего пользователя; отказ от произвольного `path`/`user` или строгая allowlist.
- Выходные данные
  - Экранирование HTML в `reviews/view`.
- Журналы
  - Ограничить доступ к `/debug/logs` только staff; исключать/маскировать чувствительные поля.
- Инструменты ассистента
  - `/assistant/execute` — требовать сессию, проверять разрешённость инструмента и аргументов для роли/владельца заказа; запрет `delete_tree`.
- Бизнес-правила
  - Игнорировать клиентский `price`, брать цену из каталога на сервере.

## Связка угроз ↔ фиксы ↔ тесты/артефакты

- SQLi и IDOR (/profile, /search)
  - Фиксы: параметризованные запросы; /profile игнорирует query id; /search только для staff
  - Тесты: `test_profile_returns_only_session_user`, `test_profile_ignores_injection_and_id`, `test_search_forbidden_for_customer`, `test_search_allowed_for_staff_only`
  - Артефакты «до»: `evidence/before/sqli_*`, `evidence/before/idor_profile_bob.json`

- Эскалация ролей заголовком (/admin/export)
  - Фиксы: проверка роли из сессии; игнор `X-Role`
  - Тесты: `test_admin_export_requires_staff_session`
  - Артефакты «до»: `evidence/before/admin_export_header_only.json`

- Подмена цены (/orders)
  - Фиксы: цена строго из каталога
  - Тесты: `test_order_price_from_catalog`
  - Артефакты «до»: `evidence/before/order_price_tamper.json`

- Доступ к файлам (/files)
  - Фиксы: только чек текущего пользователя, жёсткий allowlist пути
  - Тесты: `test_files_cannot_read_others_receipt`, `test_files_cannot_access_private_note`
  - Артефакты «до»: `evidence/before/files_bob_receipt.json`, `evidence/before/files_private_note.json`

- Stored XSS (/reviews/view)
  - Фиксы: экранирование HTML
  - Тесты: `test_reviews_view_escapes_html`
  - Артефакты «до»: `evidence/before/reviews_view.html.json`

- Небезопасный /assistant/execute
  - Фиксы: авторизация; ограничения по ролям; запрет `delete_tree`
  - Тесты: `test_assistant_requires_auth`, `test_assistant_customer_only_own_receipt`, `test_assistant_staff_can_export_but_not_delete`
  - Артефакты: `evidence/before/assistant_*`, `evidence/after/assistant_*`

- Утечки /debug/logs
  - Фиксы: доступ только staff
  - Тесты: `test_debug_logs_only_staff`
  - Артефакты «до»: `evidence/before/debug_logs.json`

## Краткие выводы

- На старте уязвимости позволяли получить/удалить данные и нарушать бизнес-правила.
- После фиксов контроль доступа и параметризация SQL закрывают основные векторы; XSS подавлен экранированием; ассистент ограничен ролями; журналы защищены.
