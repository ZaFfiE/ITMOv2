- Решение, для которого нужны альтернативы:
- Улучшение качества AI-ревью TRAINING_PR.diff за счёт: A) усиления требований к prompt в review_service, B) добавления схем валидации входного JSON для /api/reviews, C) комбинированного уточнения prompt и проверки входных данных.

  - Минимальность и локальность правок.
  - Снижение ложноположительных замечаний.

## Запрос

- Diff: @practices/practice_01/TRAINING_PR.diff
- Проблема и метрики: @practices/practice_01/problem.md

Задача:
- Сгенерируй три внешне описанные альтернативы (ветви мыслей) анализа diff и предлагаемых правок:

  - Подход B: добавление схем валидации входного JSON для /api/reviews.
  - Подход C: комбинированный — уточнение prompt и проверка входных данных.
- Для каждой альтернативы:
  - Приведи 2–3 конкретных Findings с file:line.
  - Укажи риски и воспроизводимые checks.
  - Оцени соответствие метрикам из problem.md.
- Выбери лучший подход по критериям и объясни выбор.

Формат ответа:

Инструкция по журналу Практики 2:

## Варианты решения

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A | Минимальная правка; напрямую воздействует на структуру ответа LLM (требование file:line, checks). | Не устраняет 500 при некорректном JSON; зависимость от дисциплины LLM. | Метрики: file:line ≥ 90% достижимо; риски >3 — под контролем; checks ≥1 — повышается. |
| B | Чёткий API-контракт; 4xx вместо 500; снижает шум из-за невалидных входов. | Не влияет на структуру LLM-ответа; может оставить общие ответы без evidence. | Метрики: file:line почти не растёт; риски >3 — без изменения; checks — покрытие по API. |

## Выбор

- Выбранная альтернатива: C (комбинированный подход)
- Почему: одновременно решает проблему качества вывода (file:line, checks) и устойчивости API (валидация «diff»), что напрямую соответствует метрикам и снижает ложноположительные замечания.
- Как проверим: выполнить Checks C1–C3 (см. ниже) на основе TRAINING_PR.diff и API /api/reviews, зафиксировать результаты в prompts.md.

## Alternatives A/B/C (Findings, Risks+Checks, Metrics)

Альтернатива A: Усиление требований к prompt в review_service
- Findings:
  1) practices/practice_01/TRAINING_PR.diff:20 — prompt не задаёт структуру вывода (нет требований к file:line, checks): f"Review this pull request and find problems:\n{diff}".
  2) practices/practice_01/TRAINING_PR.diff:22 — возврат только {"comment": answer} без поля evidence/checks.
  3) practices/practice_01/TRAINING_PR.diff:19–22 — отсутствуют ограничения длины diff/правила сокращения, что ведёт к общим ответам и усечению контекста.
- Риски:
  R1: Ответы без file:line и evidence (ложноположительные замечания). Реф.: diff:20–22.
  R2: Переполнение контекста LLM при больших diff, деградация качества. Реф.: diff:19–22.
- Checks:
  C1: Подать небольшой diff и проверить долю утверждений с file:line в ответе LLM — ожидание ≥ 90% после усиления prompt.
  C2: Подать diff > 20000 символов — проверить, что ответ включает явно отмеченные усечённые блоки и сохраняет структуру.
- Метрики: повышается доля file:line (цель ≥ 90%), число рисков >3 удерживается на 0, у каждого риска ≥1 check — да (C1–C2).

Альтернатива B: Схемы валидации входного JSON для /api/reviews
- Findings:
  1) practices/practice_01/TRAINING_PR.diff:36 — сигнатура create_review(payload: dict) без Pydantic-схемы; нет контрактной валидации.
  2) practices/practice_01/TRAINING_PR.diff:37 — payload["diff"] вызывает KeyError при отсутствии ключа → 500 вместо 422.
  3) practices/practice_01/TRAINING_PR.diff:35–38 — нет проверок типа/ограничений длины diff (строка, max_len).
- Риски:
  R1: 500 Internal Server Error на валидных 4xx сценариях (ошибка UX и мониторинга). Реф.: diff:37.
  R2: Неконсистентные ответы API без явного контракта (сложно воспроизводить). Реф.: diff:35–38.
- Checks:
  C1: POST /api/reviews с {} — ожидание 422, фактически при текущем коде 500 (KeyError). После схемы — 422 c сообщением о недостающем поле.
  C2: POST /api/reviews с {"diff": 123} — ожидание 422 (тип не string). После схемы — 422 с указанием типа.
  C3: POST с {"diff": "a"*50000} — ожидание 413/422 по политике; после схемы — 422 (max_length) или 413 (reverse-proxy), документировано.
- Метрики: напрямую не повышает долю file:line; снижает риски API-входа; checks воспроизводимы; рисков >3 — 0.

Альтернатива C: Комбинированный — уточнение prompt и проверка входных данных
- Findings: объединяет A и B (см. ссылки):
  1) practices/practice_01/TRAINING_PR.diff:20 — уточнить prompt: требовать для каждого finding ссылку file:line и описания checks.
  2) practices/practice_01/TRAINING_PR.diff:22 — расширить структуру ответа: {comment, evidence, checks}.
  3) practices/practice_01/TRAINING_PR.diff:35–38 — ввести Pydantic-схему для {diff:str, max_len<=N} и 422 при нарушениях.
- Риски:
  R1: Недисциплинированный вывод LLM при сложных кейсах — смягчается жёсткой структурой и примерами.
  R2: Отторжение чрезмерно длинных входов — документировать лимит и повед. 4xx.
- Checks:
  C1: Повтор C1(A) — доля file:line ≥ 90% в ответе.
  C2: Повтор C1(B) — {} → 422 с сообщением о «diff».
  C3: Повтор C3(B) — длинный diff → 422/413; ответ LLM не вызывается.
- Метрики: достигаются все цели — file:line ≥ 90%; рисков >3 — 0; checks ≥1 на риск — есть (C1–C3).

## Decision

Подход C выбран как баланс качества вывода и надёжности входа при минимальном объёме правок.
